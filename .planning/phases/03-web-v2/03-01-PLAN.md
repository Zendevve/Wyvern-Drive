# Phase 3: Web v2 File Manager

**Goal**: A working Next.js 14 SPA where the user can log in, browse their Discord-backed file tree, upload (drag-drop), download, rename, move, and delete.

**Depends on**: Phase 2
**Requirements**: FS-01..08, WEB-01..07
**Status**: Pending
**Plans**: 4

## Context

The web app is the primary user-facing surface. It must feel like a modern cloud drive (think Dropbox / Google Drive UX) while hiding the Discord-as-storage weirdness.

**Stack** (locked): Next.js 14 App Router, TypeScript, Tailwind, shadcn/ui, Zustand.

**Zustand store creation pattern in Next.js App Router**: use `useState(() => createStore())` per-request on the server, and import store creator functions on the client. Avoid global store initialization.

## Plan 03-01: Next.js 14 scaffold, shadcn/ui, Tailwind, auth pages, account picker

**Tasks**:
1. **Next.js 14 setup**: App Router, TypeScript, Tailwind, ESLint, `next.config.mjs`. No `pages/` dir.
2. **shadcn/ui init**: `pnpm dlx shadcn@latest init` style. Pick neutral base color, dark-first theme.
3. **shadcn components used**: `button`, `input`, `dialog`, `dropdown-menu`, `context-menu`, `progress`, `breadcrumb`, `tooltip`, `toast`, `skeleton`, `sheet`, `popover`, `scroll-area`, `separator`.
4. **Auth flow**:
   - `/login` page: single text input for Discord user token + "Continue" button.
   - `POST /auth/login` (proxied to server).
   - Cookie-based session; middleware (`middleware.ts`) redirects unauthenticated users to `/login`.
5. **Account picker** (`/setup` or first-login flow): if no accounts, prompt to add one (paste token). If multiple accounts, show picker.
6. **Layout**: top nav with logo, account avatar, theme toggle. Sidebar (will be populated in 03-02). Main content area.
7. **Theme**: dark default, light optional. Discord blurple accent `#5865F2`.
8. **Login state via Zustand**: `useAuthStore` with `user`, `accounts`, `activeAccountId`, `isAuthenticated`, `login`, `logout`, `addAccount`, `setActiveAccount`.

## Plan 03-02: Zustand stores, file list/grid components, context menu

**Tasks**:
1. **`useFsStore`**: `cwd`, `entries` (children of cwd), `selected`, `isLoading`, `error`. Actions: `navigate(path)`, `refresh()`, `select()`, `clearSelection()`.
2. **API client** (`src/lib/api.ts`): thin fetch wrappers for `/files/list`, `/files/create-folder`, etc. Uses `credentials: 'include'`.
3. **Components**:
   - `<FileList>`: virtualized table (use `@tanstack/react-virtual`) with columns: icon, name (sortable), size (sortable), modified (sortable).
   - `<FileGrid>`: card-based grid with thumbnails (filled in Phase 10).
   - `<ViewToggle>`: switches between list and grid; persisted in localStorage.
   - `<Breadcrumb>`: derived from `cwd`; clickable segments.
   - `<Sidebar>`: storage stats (placeholder for now), account picker, nav links (Files / Shared / Trash — placeholders).
   - `<ContextMenu>`: shadcn `ContextMenu`; items: Open, Rename, Move, Download, Share (Phase 9), Delete.
4. **Routing**: `/` is the file manager root. Folder navigation is by path (e.g. `/?path=/photos/2024`); deep-link-friendly.
5. **Sort/filter**: clickable column headers for sort. Filter input above the list (substring on name).
6. **Keyboard**: arrow keys to navigate, Enter to open, Delete to remove, F2 to rename.

## Plan 03-03: Drag-drop upload, download, progress, queue manager

**Tasks**:
1. **Drop zone**: wraps the main content area; visual highlight on `dragenter`.
2. **`<UploadQueueProvider>`**: context that holds the global upload queue.
3. **Upload engine** (`src/lib/uploader.ts`):
   - `enqueue(file: File, path: string)`: adds to queue, starts processing.
   - Uses `@disbox/shared` `chunkFile` + `hashChunk`.
   - Posts each chunk to `POST /files/upload` (server can accept single chunks or the whole file; decide in this plan).
   - **Decision point**: does the server accept whole-file upload, or chunk-by-chunk? Recommend **whole-file upload** for v1 simplicity; server handles the chunking. This means the SDK is used in the server, not the web client. The web client sends `multipart/form-data` of the whole file.
   - Wait — re-evaluating: web client must chunk for E2EE (Phase 5). For Phase 3 (no E2EE), simpler: web sends whole file, server chunks. SDK is server-side only in Phase 3. Plan accepts this trade-off.
4. **Per-file progress UI**: `<UploadQueuePanel>` drawer showing queued/in-progress/complete with bars and bytes.
5. **Download**:
   - `GET /files/download/:id` returns the file as a stream.
   - Web app uses `showSaveFilePicker` (File System Access API) for "save to disk", with fallback to anchor-click for browsers without FSA.
6. **Cancellation**: each upload has a cancel button → AbortController.
7. **Concurrency**: max 3 concurrent uploads (configurable).

## Plan 03-04: Rename, move, delete, recursive delete, folder upload

**Tasks**:
1. **Rename**: inline editor in the list (F2 or double-click name). PATCH `/files/:id` `{ name }`.
2. **Move**: drag a file/folder row onto a folder. POST `/files/:id/move` `{ newParentId }`. Optimistic UI: update local store first, roll back on error.
3. **Delete**: context-menu or Delete key. DELETE `/files/:id`. For folders: confirm recursive delete (server must support it).
4. **Recursive delete on server**: Phase 2 already has `DELETE /files/:id` that cascades to children + chunks. Verify with a test.
5. **Folder upload**: drop a folder on the drop zone → enumerate `webkitGetAsEntry()` → recursively POST each file with the relative path as a prefix.
6. **Empty states**: "This folder is empty — drag files here to upload" CTA.
7. **Error toasts**: shadcn `Toast` for all failures with a "Retry" button where appropriate.

**Acceptance**:
- User can log in with a Discord user token, see their file tree, upload via drag-drop, download, rename, move, delete, upload folders.
- All 15 requirements (FS-01..08, WEB-01..07) pass.
- Page reload restores session and last cwd.
- App is responsive down to 768 px (mobile polish is Phase 9).
