# Phase 10: Polish

**Goal**: Previews, multi-file zip download, persistent upload queue, and auto-retry.

**Depends on**: Phase 3 (and gains richness from Phases 6, 8)
**Requirements**: FS-09, WEB-08, POL-01, POL-02, POL-03, POL-04
**Status**: Pending
**Plans**: 3

## Context

Phase 10 is the "feels like a real product" phase. The features are individually small but they collectively make the difference between a tool and a product. Done at the end because they all benefit from stable prerequisites (file system, search, sharing).

## Plan 10-01: Thumbnail/preview service (server-side thumb generation) + preview panel UI

**Tasks**:
1. **Server thumbnails** (`apps/server/src/services/thumbnails.ts`):
   - On upload, generate a 200×200 thumbnail for images (use `sharp`).
   - For videos: extract first frame with `ffmpeg` (optional — `ffprobe` + `ffmpeg` must be present; document in README).
   - For audio: generate a small waveform PNG (or just an icon for v1).
   - For docs: use a generic icon.
   - Store thumbnails in a `thumbnails` table (hash, mime, bytes).
2. **Preview panel** (`<PreviewPanel>`): right-side sheet (shadcn `Sheet`). Renders:
   - Image: `<img>`.
   - Video: `<video controls>`.
   - Audio: `<audio controls>` + waveform.
   - PDF: `<embed>` or `<iframe>`.
   - Text/code: `<pre>` with syntax highlighting (`shiki`).
3. **Tests**: thumbnail generation correctness (visual regression optional), preview panel render for each type.

## Plan 10-02: Client-side zip streaming for multi-download

**Tasks**:
1. **Multi-select**: already in Phase 3 (checkboxes). Verify behavior.
2. **Client-side zip**: use a streaming zip library (`client-zip` or `fflate`). Stream chunks as they download from the server; zip them in-memory; hand the final blob to the save picker.
3. **Folder download**: download a folder by enumerating children recursively and zipping them in the same stream.
4. **Progress**: combined progress = (bytes downloaded so far) / (total bytes expected).
5. **Tests**: download a multi-file zip; verify the zip opens and contains the right files at the right paths.

## Plan 10-03: IndexedDB-backed upload queue with auto-retry

**Tasks**:
1. **Persistent queue**: the upload queue from Phase 3 lives in memory. Migrate to IndexedDB (`src/lib/queue-db.ts`). On startup, rehydrate the queue.
2. **Auto-retry**: failed chunks are retried with exponential backoff (matches server's DISC-05). Max 5 attempts. After max, mark as failed-permanently; user can manually retry.
3. **Crash recovery**: kill the tab mid-upload → on next launch, the queue picks up where it left off. Verify with a manual test (DevTools "Application > Service Workers > Stop") and an automated test (close the worker context, reopen, assert queue resumes).
4. **Concurrency**: max 3 concurrent uploads. When one completes, the next queued one starts.
5. **Cancel**: each queue item has a cancel button → AbortController. Cancelled items are removed from the queue (not retried).
6. **Visual states**: queued (clock icon), in-progress (spinner), retrying (warning + countdown), complete (check), failed (red X + retry).

**Acceptance**:
- All 4 polish requirements pass.
- Thumbnails visible in the file list at 200×200.
- Preview panel renders for image, video, audio, PDF, text.
- Multi-download produces a valid zip.
- Queue survives a hard refresh.
- Failed uploads auto-retry up to 5 times.
