# Phase 8: Sharing v2

**Goal**: Shortlinks for any file with optional expiration and password protection, accessible without login.

**Depends on**: Phase 3
**Requirements**: SHARE-01, SHARE-02, SHARE-03, SHARE-04
**Status**: Pending
**Plans**: 2

## Context

v1 implemented sharing by encoding the Discord attachment URLs into a hash fragment of the share URL (deflate + base64). That works but has a hard cap on file size, exposes the URLs in the URL bar, and isn't revocable.

v2's sharing is server-mediated: a shortlink is a row in the `shares` table; the public download endpoint serves the file with no auth check. The shortlink can have an expiration and a password. For E2E files, the shortlink includes a wrapped file key (the password, if set, is one factor; the user can also choose to "share the file key out-of-band" by setting a separate `shareSecret`).

**Public endpoint**: `GET /s/:slug` returns either the file (if no password) or a password prompt UI (small HTML page). The UI is a static React app or a server-rendered page — pick a small one for v1.

## Plan 08-01: Shortlink schema, share creation/revocation, public download endpoint

**Tasks**:
1. **Schema**: `shares (slug pk, fileId fk, accountId fk, createdAt, expiresAt?, passwordHash?, wrappedFileKey?, wrappedFileKeyIv?)`. Slug is 8 random base64url chars.
2. **Server endpoints**:
   - `POST /shares` (auth) — body `{ fileId, expiresIn?, password? }` → returns `{ slug, url }`.
   - `DELETE /shares/:slug` (auth) — revoke.
   - `GET /shares?fileId=` (auth) — list shares for a file.
   - `GET /s/:slug` (public) — if no password, redirect to `/s/:slug/download`; if password, render password prompt.
   - `POST /s/:slug/unlock` (public) — body `{ password }` → sets a short-lived signed cookie for that slug.
   - `GET /s/:slug/download` (public + cookie or no-password) — streams the file.
3. **Expiration**: server checks `expiresAt` on every public request. Expired shares return 410 Gone.
4. **Password**: hash with Argon2id (or scrypt) on the server. Cookie-based unlock to avoid re-prompting per chunk.
5. **Tests**: integration test creating a share, downloading it, expiring it (manually advance clock), password-protecting it, revoking it.

## Plan 08-02: E2E shortlink wrapping, password prompt UI, share menu in web app

**Tasks**:
1. **E2E wrapping**: when sharing an E2E file, the user has two options:
   - **Password-only share**: the wrapped file key is encrypted with the share password (server stores the wrapped key). Recipients need the password to decrypt.
   - **Out-of-band share**: the wrapped file key is included in the share URL fragment (`#key=...`) and not sent to the server. Recipients get the key from the URL; the server only sees ciphertext.
2. **Share menu** (`<ShareDialog>`): opens from the context menu. Fields: expiration select, password (optional), copy-link button. For E2E files: radio for "share password" vs "share with link key".
3. **Public download page** (`/s/[slug]`): minimal React page; password input if needed; download button; file metadata; expiration countdown.
4. **Revoke UX**: in the file context menu, "Manage shares" shows active shares with a revoke button.
5. **Tests**: end-to-end: create E2E file, share with password, log out, open in incognito, enter password, download, verify decryption.

**Acceptance**:
- All 4 share requirements pass.
- Public download works without login.
- Expired shares return 410.
- Password-protected shares require the password to download.
- E2E shares work end-to-end with both password and out-of-band key flows.
