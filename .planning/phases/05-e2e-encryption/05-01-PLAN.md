# Phase 5: Client-Side E2E Encryption

**Goal**: Optional zero-knowledge mode where the user sets a master passphrase, all chunks are encrypted with AES-256-GCM before upload, and the server only sees ciphertext.

**Depends on**: Phase 3
**Requirements**: E2EE-01, E2EE-02, E2EE-03, E2EE-04
**Status**: Pending
**Plans**: 3

## Context

E2EE is the differentiator vs Google Drive / Dropbox. The architecture is: master passphrase → Argon2id KDF → master key (in memory only) → per-file key (random) → AES-256-GCM with chunk index as AAD. The server stores ciphertext + the wrapped per-file key (wrapped by the master key). It cannot decrypt.

**Prior art**: the deleted v2 attempt implemented this with Argon2-browser in a Web Worker. That approach worked; v2 reuses the pattern. **Re-evaluating**: the user wants AES-256-GCM in the SDK. Argon2 stays in a Web Worker. The SDK is a pure module; the worker is a thin app-level wrapper.

**Critical**: the master passphrase is **never** sent to the server. The master key lives in memory and is wiped on logout. Wrong passphrase = wrong key = decrypt fails fast (GCM auth tag fails).

## Plan 05-01: Argon2id Web Worker, master-key derivation, secret store

**Tasks**:

1. **Web Worker** (`src/workers/crypto.worker.ts`):
   - Argon2id (use `argon2-browser` or a maintained alternative).
   - Parameters: `timeCost: 3, memoryCost: 64 * 1024, parallelism: 1` (or up-to-date OWASP recommendations).
   - Messages: `{ type: 'derive', passphrase, salt } → { type: 'derived', key }`.
2. **Master key derivation**:
   - Salt: random 16 bytes, generated on first E2E setup, stored in IndexedDB (not the key, just the salt).
   - Master key: 32 bytes, never persisted, never sent to server.
3. **Secret store** (`src/lib/secret-store.ts`): thin IndexedDB wrapper. Stores:
   - `salt` (per-account)
   - `encryptedMasterKey` (encrypted with a session-only wrapping key derived from a "device secret" + account id — opt for simpler: don't persist the master key; require re-entry each session)
   - Decision: **simpler**: master key is in-memory only; session restores require passphrase re-entry. Document this trade-off.
4. **Hook** (`src/hooks/useCryptoWorker.ts`): React hook that owns the worker reference and the master key state.
5. **Crypto store** (`src/store/crypto.ts`): Zustand store for `isUnlocked: bool`, `lastUnlockError: Error | null`, `unlock(passphrase)`, `lock()`, `wipe()`.

## Plan 05-02: AES-256-GCM encrypt/decrypt wrappers in SDK with AAD

**Tasks**:

1. **Add crypto module to `@disbox/shared`** (`packages/shared/src/crypto.ts`):
   - `generateFileKey(): Uint8Array` — 32 random bytes via WebCrypto.
   - `wrapKey(fileKey, masterKey): Uint8Array` — AES-256-GCM-encrypt the file key with the master key. AAD = `accountId`.
   - `unwrapKey(wrapped, masterKey): Uint8Array` — reverse.
   - `encryptChunk(plaintext, fileKey, chunkIndex, fileId): Uint8Array` — AES-256-GCM with IV = 12 random bytes, AAD = `${fileId}:${chunkIndex}` (binary).
   - `decryptChunk(ciphertext, fileKey, chunkIndex, fileId): Uint8Array` — reverse; throws on auth-tag mismatch.
2. **Manifest update**: `FileManifest` adds `encrypted: bool`, `wrappedFileKey: Uint8Array` (only present if `encrypted: true`).
3. **Tests** in the SDK: encrypt → decrypt round-trip; tamper test (modify ciphertext → decrypt throws); reorder test (swap chunk indices → decrypt throws); AAD binding test (wrong fileId → decrypt throws).

## Plan 05-03: UI contract: passphrase gate, E2E toggle, migration flow

**Tasks**:

1. **Passphrase gate** (`<PassphraseGate>`): on first E2E setup, prompt for passphrase + confirmation. On subsequent sessions, prompt to unlock.
2. **E2E toggle in account settings**: turn E2E on per-account. Off by default. Persisted in server (account row gets `e2eEnabled: bool`).
3. **Upload flow change** (when E2E on):
   - Browser chunks the file (now using SDK on the client).
   - Encrypts each chunk with the file key.
   - Wraps the file key with the master key.
   - Sends encrypted chunks + wrapped key to server.
4. **Download flow change** (when E2E on):
   - Browser fetches encrypted chunks + wrapped key.
   - Unwraps file key with master key.
   - Decrypts chunks in order, concatenates, hands to the save flow.
5. **Migration flow for existing (non-E2E) accounts**: on enabling E2E, prompt "Encrypt existing files?" → re-upload encrypted versions. Out of scope: server-side encryption of legacy files (would break the zero-knowledge model).
6. **Lock on inactivity**: 15 min idle → auto-lock. Re-entry required.
7. **5-attempt wipe**: 5 wrong passphrases → wipe local secret store (account is still on server but inaccessible until right passphrase is provided — actually, in the no-persist model, the user would need to re-upload all files. Document this risk in the gate UI).
8. **Tests**: integration test in web app: upload a file with E2E on → assert server response has no plaintext → download with right passphrase → assert byte-equality → download with wrong passphrase → assert fail.

**Acceptance**:

- All 4 E2EE requirements pass.
- Server NEVER sees plaintext chunks for E2E accounts (verified by integration test).
- Wrong passphrase fails fast (decrypt throws within 1 chunk).
- Master key is wiped on logout.
