# Phase 07.1: Localhost database and API backend migration - Context

**Gathered:** 2026-06-03
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase delivers a fully functional, self-contained localhost backend and database for Wyvern Drive, eliminating dependencies on Supabase Cloud.

### What is in scope:
- A new Node.js Express server package written in TypeScript using SQLite (`better-sqlite3`).
- Replicating all endpoints from the Supabase Edge Function API on the local Express server.
- Storing files, file versions, file chunks, and user profiles in a local SQLite database.
- A custom, lightweight authentication system (signup, login, sessions) integrated into the SQLite database, replacing Supabase Auth.
- A frontend Supabase adapter (`wyvern-web/src/lib/supabase.ts`) that mocks the Supabase client interface using `localStorage` and standard HTTP fetch requests to the local Express server, minimizing code modifications.
- Local storage for shared files under a dedicated directory on the local disk (instead of Supabase Storage) served by the Express server.
- Configuration options via environment variables (e.g. `VITE_API_URL`, `PORT`).

### What is out of scope:
- Migrating Discord webhook uploads (actual file chunks still upload to Discord since Discord is the primary storage mechanism).
- Local hosting of a Discord clone or replacing Discord webhooks (only the database and API metadata are hosted locally).
- Multi-region replication or distributed SQLite.
</domain>

<decisions>
## Implementation Decisions

### Local Backend Architecture
- **D-01:** Implement a Node.js Express server with TypeScript (`wyvern-backend` or `server/`) that serves as the local API.
- **D-02:** Use `better-sqlite3` as the database driver, storing metadata in a local SQLite database file (e.g., `wyvern.db` at the root of the backend directory).
- **D-03:** Initialize the SQLite database automatically on startup using migration scripts or raw SQL DDL blocks representing the existing schema (`user_profiles`, `files`, `file_versions`, `file_chunks`, `shares`).

### Authentication & Sessions
- **D-04:** Implement local credentials auth (sign up and sign in using email/password) on the Express backend. Use a `users` table to store email and hashed passwords (using a fast hashing library like `bcryptjs` or a Node crypto-native implementation).
- **D-05:** Return a simple JSON Web Token (JWT) or session token on login/signup, which the frontend stores in `localStorage`.
- **D-06:** Mock the Supabase client's auth interface (`supabase.auth.getSession()`, `supabase.auth.onAuthStateChange()`, `supabase.auth.signInWithPassword()`, `supabase.auth.signUp()`, `supabase.auth.signOut()`) in `wyvern-web/src/lib/supabase.ts` to query this local token and update local state seamlessly.

### File Sharing & Local Storage
- **D-07:** Replace Supabase Storage for small shared files with local file storage. Small files shared under the threshold (1MB) will be saved to a local folder (e.g., `data/shares/`) on the server disk.
- **D-08:** Expose a local public endpoint (e.g., `/shares/download/:shareId`) from Express to download files directly from local shares or fetch the Discord chunks for larger files.

### Developer Experience / Run Scripts
- **D-09:** Add a run script to start the local backend server (e.g., `npm run dev` in the backend directory).
- **D-10:** Update the root `package.json` to allow running both frontend and backend concurrently (e.g., using `concurrently` or similar).

### the agent's Discretion
- The folder structure of the new backend package (e.g., `wyvern-web/server` vs `wyvern-backend` or root `wyvern-server`).
- The choice of password hashing library and session token format, provided it remains lightweight and requires no external cloud services.
- The precise port number for the local Express server (e.g. `3001` to avoid Vite's default `3000`).
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `supabase/functions/api/index.ts`: The Deno-based Supabase Edge Function contains all route logic (file management, sharing creation, chunk pagination, versioning). This logic can be directly ported to Express routes with minor adjustments for Deno-to-Node compatibility.
- `supabase/migrations/`: Contains the complete schemas for `files`, `file_versions`, `file_chunks`, `user_profiles`. These can be mapped to SQLite-compatible SQL CREATE TABLE queries.

### Integration Points
- `wyvern-web/src/lib/supabase.ts`: Replaces the real Supabase Client with our mock/local adapter. All components and stores that rely on `supabase` will import from this file, ensuring no changes to components are necessary.
- `wyvern-web/src/lib/wyvern-file-manager.ts`: The variable `API_URL` should be configured dynamically or via environment variable (`import.meta.env.VITE_API_URL` or fallback to `http://localhost:3001/functions/v1/api` or `/api`).
</code_context>

## Specific Ideas
- To keep setup simple and self-contained, the Express server should automatically run migrations on startup (e.g. checking if tables exist and executing the DDL scripts).
- An SQLite database file should be gitignored (e.g., adding `*.db` and `*.db-journal` to `.gitignore`).
