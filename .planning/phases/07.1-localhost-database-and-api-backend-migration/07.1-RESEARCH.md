<user_constraints>
## User Constraints (from CONTEXT.md)

### Locked Decisions
- **Database Engine:** SQLite (via `better-sqlite3` driver) storing metadata in a local database file (`data/wyvern.db`).
- **Server Platform:** Node.js Express server + TypeScript (`wyvern-backend` package).
- **Authentication:** Custom Express Auth + SQLite Users Table + Mock Client Adapter in `wyvern-web/src/lib/supabase.ts`.
- **File Sharing Storage:** Store shared files under a dedicated folder on local disk (`data/shares/`) instead of Supabase Storage.
- **In-Scope:** All endpoints from the Supabase Edge Function API replicated on the local Express server.
- **Out-of-Scope:** Discord webhook storage migration (file chunks remain uploaded to Discord).

### the agent's Discretion
- The folder structure of the new backend package (we will name it `wyvern-backend` in the workspace root).
- Choice of password hashing library (we will use `bcryptjs` for standard Node compatibility).
- Port number: `3001` to avoid Vite's default `3000`/`5173` ports.
</user_constraints>

<research_summary>
## Summary

This research outlines the design for migrating Wyvern Drive's database, authentication, and file storage APIs to a local, self-contained Express + SQLite backend. 

By replacing the cloud dependency of Supabase with a local Node server, the app is made entirely localhost-compliant. We will model the database schemas using `better-sqlite3`'s synchronous execution (which is extremely fast and robust for local SQLite usage). To preserve the existing frontend's React components, we will implement a mock client adapter in `wyvern-web/src/lib/supabase.ts` that conforms to the public API surface of the Supabase JS SDK, but makes REST calls to the local Express server and manages authentication tokens in `localStorage`.

**Primary recommendation:** Build `wyvern-backend` as a new TypeScript npm package. Implement database initialization on startup using automated SQL execution. Replace the `@supabase/auth-ui-react` component in the frontend with a custom React form complying with the accessibility rules outlined in `AGENTS.md`.
</research_summary>

### Pattern 1: Database Startup Initialization
To keep deployment zero-setup, the server should run database schema scripts synchronously during startup:
```typescript
import Database from 'better-sqlite3';
import path from 'path';

const dbPath = path.resolve(process.env.DB_PATH || './data/wyvern.db');
export const db = new Database(dbPath);

// Enable WAL mode for performance
db.pragma('journal_mode = WAL');

export function initDatabase() {
  db.exec(`
    CREATE TABLE IF NOT EXISTS users (
      id TEXT PRIMARY KEY,
      email TEXT UNIQUE NOT NULL,
      password_hash TEXT NOT NULL,
      created_at TEXT DEFAULT (datetime('now')),
      updated_at TEXT DEFAULT (datetime('now'))
    );
    -- Other tables...
  `);
}
```

### Pattern 2: Mocking Supabase Client
The client in `wyvern-web/src/lib/supabase.ts` should return a matching shape for auth and databases:
```typescript
class MockSupabaseClient {
  auth = {
    async signUp({ email, password }) {
      // POST /api/auth/signup
    },
    async signInWithPassword({ email, password }) {
      // POST /api/auth/login -> store token in localStorage
    },
    async signOut() {
      // clear token
    },
    async getSession() {
      // return session structured object if token exists
    },
    onAuthStateChange(callback) {
      // register listener and trigger on change events
    }
  };

  // Keep it compatible for simple user_profiles calls
  from(table: string) {
    if (table === 'user_profiles') {
      return {
        select: () => ({
          eq: (field: string, value: string) => ({
            single: async () => {
              // GET /api/auth/me -> return profile info
            }
          })
        }),
        upsert: (data: any) => ({
          // POST /api/auth/profile-update
        })
      };
    }
    throw new Error(`Direct table access for ${table} is not supported in Localhost mode.`);
  }
}
```

### Anti-Patterns to Avoid
- **Not Sanitizing Inputs / No Parameterized Queries:** SQLite is prone to SQL Injection. Always use `db.prepare('...').run(param1, param2)` instead of template string interpolation.
- **Storing Plaintext Passwords:** Always hash passwords with bcrypt before storing them in SQLite.
- **Mocking the entire Supabase Client API needlessly:** Only mock the auth and profiles logic. Let the actual files/folders logic call the localhost endpoints directly, which keeps code modifications extremely clean.
</architecture_patterns>

<dont_hand_roll>
## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Password cryptography | Custom hashing | `bcryptjs` | Custom hashes (e.g. SHA-256 without salt) are highly vulnerable to rainbow table attacks. |
| Session encryption | Custom encryptions | `jsonwebtoken` | Standard JWT libraries handle signature verification and expiry checks correctly. |
| SQLite bindings | Raw node bindings | `better-sqlite3` | Native Node bindings are difficult to write and maintain without memory leaks. |
</dont_hand_roll>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: SQLite File Locking
**What goes wrong:** SQLite database gets locked during concurrent writes, throwing `SqliteError: database is locked`.  
**How to avoid:** Enable WAL (Write-Ahead Logging) mode on database initialization: `db.pragma('journal_mode = WAL');`. WAL permits concurrent readers while writing is in progress.

### Pitfall 2: CORS Blocking
**What goes wrong:** Frontend fails to call API endpoints, browser throws CORS errors.  
**How to avoid:** Correctly configure Express CORS middleware to allow headers, cookies, and specified origins.

### Pitfall 3: Large Payloads & Timeout
**What goes wrong:** Uploading metadata containing thousands of chunk objects causes timeouts or memory issues.  
**How to avoid:** Keep metadata size within bounds and ensure better-sqlite3 handles single-transaction batch inserts using `db.transaction()`.
</common_pitfalls>
