# Phase 2: Server v2 Core

**Goal**: Hono server with JWT auth, Drizzle/SQLite schema, account CRUD, and Discord proxy that chunks + uploads + downloads via `discord.js-selfbot-v13` with rate-limit awareness.

**Depends on**: Phase 1
**Requirements**: AUTH-01, AUTH-02, AUTH-03, ACCT-01, ACCT-02, ACCT-03, DISC-01, DISC-02, DISC-03, DISC-04, DISC-05
**Status**: Pending
**Plans**: 3

## Context

The server is the **only** component that talks to Discord. Web app talks to the server over REST. The server:

- Authenticates users by validating their Discord user token against `/users/@me` (one round-trip per login).
- Stores a JWT in an httpOnly cookie for session.
- Chunks uploads, uploads chunks to a private Discord server/channel via `discord.js-selfbot-v13`, persists the chunk manifest in SQLite.
- Downloads: fetches chunk attachments from Discord, reassembles, streams to client.
- Rate-limit aware: ~5 messages / 5 s per channel. Use a queue with backoff.
- Chunk dedup by SHA-256.

**Risk**: This is the riskiest phase. Discord API quirks, rate limits, and the self-bot library are all in play. Plan extra verification (integration tests against a mocked Discord API).

## Plan 02-01: Hono scaffold, Drizzle schema, JWT auth, account endpoints

**Tasks**:

1. **`apps/server` scaffold**: Hono app, `tsx watch` for dev, `tsc` for build. Env config via `process.env` with `dotenv`.
2. **Drizzle schema** (`src/db/schema.ts`):
   - `accounts`: `id (uuid), userId (snowflake), username, discriminator, hasNitro (bool), addedAt`.
   - `nodes`: `id, parentId (fk nodes), name, type ('dir'|'file'), ownerId (fk accounts), createdAt, updatedAt`.
   - `files`: `id (fk nodes), size, mime, manifestJson (text, JSON of ChunkRef[]), encrypted (bool)`.
   - `chunks`: `hash (pk), size, discordMessageId, discordChannelId, uploadedAt, refCount (int)`.
3. **Migrations**: `drizzle-kit` config + initial migration.
4. **JWT auth** (`src/auth/jwt.ts`): `sign(userId, accountId)`, `verify(token)`. Use `jose`. Secret from `process.env.JWT_SECRET`.
5. **Auth middleware** (`src/auth/middleware.ts`): Hono middleware that reads the `token` cookie, verifies, attaches `userId` + `accountId` to context.
6. **Discord token validation** (`src/discord/validate.ts`): `validateToken(token) → { userId, username, hasNitro }` via `https://discord.com/api/v9/users/@me`.
7. **Endpoints**:
   - `POST /auth/login` — body `{ token }` → validate, upsert account, sign JWT, set cookie.
   - `POST /auth/logout` — clear cookie.
   - `GET /auth/me` — return current user + active account.
   - `GET /accounts` — list accounts for current user.
   - `POST /accounts` — add a new account (validates token first).
   - `DELETE /accounts/:id` — remove account (revoke JWT, do not delete files).
8. **Tests**: vitest with supertest-style fetch. Cover login → me → logout, account add/list/remove, JWT expiry.

## Plan 02-02: Discord proxy client with rate-limit queue + chunked upload/download

**Tasks**:

1. **Discord client wrapper** (`src/discord/client.ts`):
   - `createDiscordClient(token): Client` — wraps `discord.js-selfbot-v13` Client.
   - Lazy login (only on first request); cache one client per account in memory.
   - On login, ensure a private server + channel exists; cache the channel id.
2. **Rate-limit queue** (`src/discord/queue.ts`):
   - `RateLimitedQueue` class with per-channel serialization.
   - Tracks Discord response headers (`X-RateLimit-Remaining`, `X-RateLimit-Reset-After`).
   - On 429: respects `retry_after`. Default pacing: 5 messages / 5 s.
3. **Upload pipeline** (`src/discord/upload.ts`):
   - `uploadChunks(accountId, chunks: Chunk[]): Promise<ChunkRef[]>`.
   - For each chunk: check `chunks` table for existing hash; if present, reuse `discordMessageId`.
   - Else: send as Discord message attachment, insert row in `chunks` table, return ref.
   - Retry on 429 / network errors with exponential backoff (1/2/4/8/16 s, max 5).
4. **Download pipeline** (`src/discord/download.ts`):
   - `downloadChunks(refs: ChunkRef[]): AsyncIterable<Uint8Array>`.
   - Fetches `https://cdn.discordapp.com/attachments/...` URLs in parallel (max 8 concurrent).
   - Returns a stream so the server can pipe to the HTTP response.
5. **File endpoints**:
   - `POST /files/upload` — multipart, chunks the upload (using SDK), uploads via Discord client, writes manifest row, returns `fileId`.
   - `GET /files/download/:id` — loads manifest, streams chunks to response.
   - `DELETE /files/:id` — deletes Discord messages, decrements `refCount`, deletes row.
6. **Tests**: unit tests for queue logic (mocked timers), upload retry (mocked 429), download parallelism. Integration tests in Plan 02-03.

## Plan 02-03: Integration tests against a mocked Discord API

**Tasks**:

1. **Mock Discord API server** (`tests/discord-mock.ts`): an in-process Hono server that mimics the Discord REST API surface used by the client: `GET /users/@me`, `POST /channels/:id/messages` (with attachment), `GET /messages/:id`, `DELETE /messages/:id`. Holds uploaded "messages" in memory.
2. **Mock Discord CDN** (`tests/cdn-mock.ts`): serves the attached files back via `/attachments/:channelId/:attachmentId/:filename`.
3. **E2E test scenarios**:
   - Login → upload 30 MB file → verify it chunks into 25 MB pieces → verify Discord mock received the right number of messages → download → verify byte-equality.
   - Upload same file twice → verify second upload produces zero new Discord messages (dedup).
   - Force the mock to return 429 on one message → verify retry succeeds.
   - 50 MB file with `hasNitro: true` → verify 50 MB chunks.
4. **CI integration**: these tests run as part of `pnpm test` in `apps/server`.

**Acceptance**:

- `pnpm --filter @disbox/server test` passes (all unit + integration).
- Server can be started with `pnpm --filter @disbox/server dev` and accepts a real Discord user token (manual smoke test; not in CI).
- All 11 requirements (AUTH-01..03, ACCT-01..03, DISC-01..05) pass.
